How to read this document. Boxes and arrows show which part talks to which. “Frontend” is everything that runs on the user’s phone or in their browser. “Backend” is everything that runs on servers NESBA rents (Supabase, LiveKit, Stripe). NESBA runs no servers of its own: every backend piece is a managed service.

5 · Backend: Supabase services

Supabase is NESBA’s main backend: database, accounts, files, live updates and server code in one managed service (region: EU · Frankfurt).

Postgres database

About 45 tables. Every table has row-level security: rules in the database decide which rows each signed-in user may read or change, so the app cannot leak data even if a screen has a bug. Sensitive actions (grading, payments, moderation) run as checked database functions.

Auth

Accounts with email and password, or Google / Apple. Each account has a profiles row with name, photo, role (student, teacher, mentor, organization, admin) and onboarding status. A trigger stops users from changing their own role or verification.

Realtime

The app subscribes to new messages, notifications and live-room changes, so pop-ups, unread counts and the live room update instantly.

Migrations

Every database change is a numbered SQL file in src/sql (001 → 034), run in order in the Supabase SQL editor. This is the history of the database.

Creator setup

  • Creator Studio → Payouts → Connect Stripe (Express, NL)
  • Prices can only be set once Stripe can pay the creator

Safety rules

  • Only the webhook can mark a purchase as paid
  • Phone apps send buyers to the website (no app-store fees)

17 · Security model

Data access

  • Row-level security on every table: users only see and change what the rules allow
  • Privileged changes (roles, grading, payments, moderation) only through checked database functions
  • Internal functions are not callable from the API (checked by Supabase’s security advisor)

Accounts

  • Passwords handled by Supabase Auth (never stored by NESBA)
  • No public “does this email exist?” lookup
  • Users cannot raise their own role or verification
  • to do turn on leaked-password protection

Payments

  • Card and bank details go straight to Stripe; NESBA never sees them
  • Prices come from the database, not from the app
  • Webhook requests must carry Stripe’s signature
  • Return links only to NESBA’s own website

Content & files

  • Uploads only into the user’s own folder
  • Private files (messages, recordings) via short-lived signed links
  • Locked lessons and paid courses blocked in the database, not only in the app
  • Production builds hide debug logs

20 · Go-live checklist

  1. Register the company; activate the Stripe account (verify business, bank).
  2. Stripe live mode: new webhook (same URL, 5 events); replace STRIPE_SECRET_KEY and STRIPE_WEBHOOK_SECRET.
  3. Choose hosting and domain; set SITE_URL; add the domain to Supabase Auth URLs.
  4. Upgrade Supabase to Pro; turn on leaked-password protection.
  5. Fill in the contact email on the legal pages; have Privacy and Terms reviewed.
  6. Recordings: S3 access keys in Supabase; enable recording in LiveKit.
  7. Phone apps: eas init, test builds, App Store / Google Play listings.
  8. Install Docker; local test database; Strix security scan.
  9. End-to-end tests: sign-up, course purchase + refund, private session, live room, push.
  10. Closed beta with a small group; collect feedback; then open to the public.
